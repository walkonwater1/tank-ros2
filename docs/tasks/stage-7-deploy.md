## S7-01 · Docker Compose 整套环境

| 状态 | 依赖 | 硬件 | 预计 |
|---|---|---|---|
| TODO | S3-05、S6-03 | 否 | 1~2 天 |

**目标**：一条命令拉起完整软件栈，环境可复制。

**步骤**
1. 基于 `ros:humble`（或对应发行版）写基础镜像：
   - 安装 `ros2_control`、`nav2`、`slam_toolbox`、驱动包
   - 非 root 用户 + `dialout` 组
2. 工作区挂载而非打进镜像，代码改动不用重建。
3. Compose 服务划分：
   - `bringup`（bridge / controller）
   - `nav2`（可选）
   - `record`（rosbag2）
   - `monitor`（diagnostics）
4. DDS 网络：`network_mode: host` 或明确配置 `ROS_DOMAIN_ID` 与组播；容器内 IPC 视情况开启。
5. 设备访问：`/dev/tank` 通过 `devices:` 映射。
6. 写 Dockerfile 版本锁定和构建缓存策略。

**验收**
- [ ] `docker compose up` 一键起停
- [ ] 容器内能看到宿主机话题
- [ ] 串口设备可访问
- [ ] 镜像可重建、版本可追溯
- [ ] 冷启动时间有记录

**风险**：DDS 在容器网络下的发现问题；权限；镜像体积。

## S7-02 · 版本化发布与回滚

| 状态 | 依赖 | 硬件 | 预计 |
|---|---|---|---|
| TODO | S2-02、S7-01 | 是 | 1 天 |

**目标**：任何一次部署都能回到上一个可用版本。

**步骤**
1. 定义版本号规则：固件、ROS2 包、配置三者分开记录。
2. 固化一份 `docs/env.md`，随版本更新。
3. 打包方式二选一：
   - 镜像 tag（推荐，回滚最快）
   - `colcon` 产物 + 安装脚本
4. 部署脚本：拉取 → 校验 → 切换 → 重启服务 → 健康检查。
5. 回滚脚本：切回上一个 tag/目录，重启并验证。
6. 记录一次完整的升级和回滚演练。

**验收**
- [ ] 升级脚本幂等
- [ ] 失败时自动回滚
- [ ] 健康检查覆盖串口、话题、TF
- [ ] 升级/回滚各演练一次并记录

**产出**：`deploy/` 目录 + `docs/experiments/YYYY-MM-DD-deploy.md`

## S7-03 · ESP32 OTA 与固件管理

| 状态 | 依赖 | 硬件 | 预计 |
|---|---|---|---|
| TODO | S1-05 | 是 | 1 天 |

**目标**：固件能远程升级，出错可回退，不靠拆机烧录。

**步骤**
1. 确认分区表：`ota_0` / `ota_1` 各 `0x3f0000`，具备 A/B 升级条件。
2. 选择 OTA 通道：
   - 沿用上游 OTA 服务（注意会切换小智的固件通道）
   - 自建 HTTP OTA（推荐，版本可控）
3. 自建服务：提供版本清单、bin 文件、校验和。
4. 固件侧：检查版本 → 下载 → 校验 → 切分区 → 重启 → 标记有效。
5. 保留 USB 烧录作为兜底，写好恢复步骤（0x0 合并镜像）。
6. 测试：正常升级、断电中断、坏包、回滚。

**验收**
- [ ] 远程升级成功
- [ ] 断电/坏包不会变砖
- [ ] 失败自动回退旧分区
- [ ] 恢复流程有文档
- [ ] 版本号和 git commit 可对应

**风险**：OTA 服务选错会覆盖小智官方通道；资产分区（8M SPIFFS）单独升级策略。

## S7-04 · 实时性与性能观测

| 状态 | 依赖 | 硬件 | 预计 |
|---|---|---|---|
| TODO | S3-03、S7-01 | 是 | 1~2 天 |

**目标**：知道系统的延迟花在哪，并能对关键路径做约束。

**步骤**
1. 测基线：`/cmd_vel` 发出到电机响应的端到端延迟。
2. 分段计时：ROS2 节点 → 串口 → ESP32 解析 → PWM 输出。
3. Linux 侧观测：
   - `top` / `htop`、`pidstat`、`perf`
   - `cyclictest` 测调度抖动
4. 可选：`ros2_tracing` / LTTng 看回调延迟。
5. 做对照实验：
   - 普通内核 vs `PREEMPT_RT`
   - 不同 CPU 亲和性 / cgroup 限制
   - 不同控制频率（20/50/100Hz）
6. 结论：哪些环节必须实时，哪些可以放用户态。

**验收**
- [ ] 端到端延迟有数据（P50/P99）
- [ ] 抖动有数据
- [ ] 至少一组对照实验
- [ ] 明确实时边界：ESP32 负责什么，Linux 负责什么

**产出**：`docs/experiments/YYYY-MM-DD-latency.md`

**注意**：不要为了“实时”过早换 RT 内核；先测出瓶颈。

## S7-05 · CI 与长时间稳定性测试

| 状态 | 依赖 | 硬件 | 预计 |
|---|---|---|---|
| TODO | S1-06、S2-04 | 部分 | 1~2 天 |

**目标**：代码改动有自动检查，系统能连续跑而不崩。

**步骤**
1. CI 范围：
   - 固件：`idf.py build`（可只跑板级 target）
   - ROS2：`colcon build` + `colcon test`
   - 文档/格式：`pre-commit`（可选）
2. 用 Docker 固定 CI 环境，避免“我这能跑”。
3. 静态检查：`clang-tidy`、`cppcheck`（可选）。
4. 长稳测试：
   - 连续运行 2h / 8h / 24h
   - 记录内存、CPU、串口错误、看门狗触发
   - 周期性发指令，检查是否漂移或卡死
5. 把测试脚本化，结果写进实验记录。

**验收**
- [ ] push 后自动构建
- [ ] 构建失败能定位到具体包
- [ ] 至少完成一次 8h 长稳
- [ ] 有内存/句柄泄漏检查结论
- [ ] 长稳脚本可重复执行

**风险**：CI 跑不了硬件相关测试；长稳测试需要独立机器和电源。
